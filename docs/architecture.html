WHEN THE SUPERVISOR HITS /app1/

1
Browser sends GET http://<host>/app1/ to the host on port 80.
2
Host OS forwards it to the only container bound to a host port: achievement-nginx at 172.20.0.6:80.
3
Nginx matches location /app1/, which does proxy_pass http://frontend_add/; — the trailing slash strips /app1 before forwarding.
4
Docker's embedded DNS resolves the upstream name frontend-add to its current container IP (172.20.0.4) — never hardcoded.
5
frontend-add's own Nginx (built by the multi-stage Dockerfile) receives the request on its location / block and serves the built React/Vite index.html + JS bundle via try_files.
6
Response streams back: frontend-add:80 → nginx:80 → host:80 → browser. The React app then runs client-side and issues its own API calls (e.g. to /app1/api/achievements) which repeat this same chain, ending at the backend.

WHEN THE SUPERVISOR HITS /api/achievements

1
Browser sends GET http://<host>/api/achievements.
2
Host forwards to achievement-nginx at 172.20.0.6:80 — same single entry point as any other request.
3
Nginx matches location /api/ → proxy_pass http://backend/;. The trailing slash strips /api, so FastAPI only ever sees /achievements.
4
Docker DNS resolves backend → 172.20.0.3. Uvicorn is listening on 0.0.0.0:8000 inside that container.
5
FastAPI's /achievements route runs a SQLAlchemy query. The connection string uses the service name db, never localhost — inside a container, localhost means the container itself, not the database.
6
Query hits achievement-db at 172.20.0.2:5432 (Postgres 16). Results return as JSON, retracing the same path back up to the browser: db → backend:8000 → nginx:80 → host:80.

FULL FLOW: /app2/api/achievements — the two-hop path, frontend to backend

1
Page is already loaded from /app2/. Its React code runs client-side and calls axios.get('/app2/api/achievements') — a relative path, so it resolves against whatever origin served the page: http://<host>/app2/api/achievements.
2
This is a brand new HTTP request from the browser, not a call the container makes internally. It goes back out to the host, port 80.
3
Host forwards it to achievement-nginx (main). Main nginx matches location /app2/ → proxy_pass http://frontend_list/;, stripping /app2. The request now heading to frontend-list:80 is /api/achievements.
4
This is the key hop people miss: the request lands on frontend-list's own Nginx (the one built into its Dockerfile image) — not on the backend yet. That container's nginx.conf has its own location /api/ → proxy_pass http://backend:8000/;.
5
frontend-list's nginx strips /api again and forwards to backend:8000. FastAPI now finally receives plain /achievements — two nginx hops away from the browser, zero involvement from the main nginx after step 3.
6
Response retraces: backend:8000 → frontend-list's nginx:80 → main nginx:80 → host:80 → browser. Two proxy layers, two Docker-DNS lookups (frontend-list, then backend), one HTTP round trip from the browser's point of view.

YOUR QUESTIONS, ANSWERED — TWO NGINX LAYERS, AND DOES MAIN TALK TO BACKEND DIRECTLY?

A
Only achievement-nginx is reachable from outside. frontend-add, frontend-list, and backend never publish a host port — the browser physically cannot reach them except through main nginx. That means every path the browser ever requests, for any reason, has to be matched by a location block inside main nginx's config, or nginx returns a 404 before the request goes anywhere at all.
B
That's why main nginx needed its own location /api/ block. Some request in your app (or your own curl/wget testing in section 18) was hitting /api/achievements directly — not prefixed with /app1/ or /app2/. Without a matching location, main nginx had nowhere to send it and it failed. Adding location /api/ { proxy_pass http://backend/; } gave it a direct route.
C
So yes — main nginx CAN and DOES talk to the backend directly. That's exactly the amber path in the diagram: upstream backend { server backend:8000; } plus location /api/. Zero frontend containers involved. It's the short path.
D
The other path (/app1/api/*, /app2/api/*) is a separate, longer route — the purple/teal dashed lines. Main nginx forwards into the matching frontend container first (stripping /app1 or /app2), and that frontend container's own bundled nginx.conf has to have its own /api/ block to relay the rest of the way to backend. That per-container nginx.conf isn't leftover boilerplate — it's the second leg of that specific request path, and it's why both frontend Dockerfiles copy in their own nginx.conf at build time.
E
Correcting the mental model: "frontend talks to nginx which talks to backend" isn't quite it — the frontend container itself is passive; it never initiates anything. What actually happens is the browser, after loading the React JS from a frontend container, fires a brand-new independent HTTP request back to http://<host>/.... That request re-enters through main nginx from scratch, exactly like a page load does — it does not travel container-to-container "underneath" the original page request.
